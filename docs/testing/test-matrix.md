# P0 acceptance test matrix

G0-04 · ADH v2.0 candidate · Proposed. These are test specifications for the G1 design and G2–G4 implementation gates. No product test or live provider call was run for this matrix. The five historical prototype tests cover a subset of auth, scoped history and manual imports. The [requirement register](../requirements/traceability.md) maps business requirements to these case families. Each family requires both columns to pass.

## Harness and fixtures

Use a fresh, isolated PostgreSQL database, real migrations, an injectable UTC clock, synchronization barriers and a recording fake ProviderPort transport. Never use wall-clock sleeps to make ordering assertions. Seed two synthetic owners, two same-owner projects A/B, a second-owner project C, distinct marker strings per project, and a disabled official provider. Use two confirmed fake model families, a second alias of one family, a dynamic unknown router and user-declared manual inputs. Include Unicode, leading spaces, duplicates, invalid references, denied context and a fake secret canary. Stub no authorization, transaction, uniqueness or budget checks in integration tests. Record the number, destination, allowed input and attempt ID of transport calls in test memory. Disable network egress to real providers in CI. Optional live qualification has its own opt-in and separate evidence.

The expected G3/G4 record for each test contains case ID/variant, requirement and card IDs, frozen SHA, fixture version, exact commands, runner/DB versions, expected/actual results, redacted failures and CI artifact location. Keep the summary in `docs/test-reports/C-xxx.md` and retain the CI evidence. A skipped live test is recorded as skipped. Raw confidential prompts, keys and session tokens must never enter reports.

## Comparison quality fixtures

Use these neutral fixed inputs and a reviewed expected-output manifest. Freeze lexical source locations using exact source substrings plus stable response IDs according to the report contract. Expected semantic assertions allow different report wording. For fixtures with enough evidence, an always-empty report fails.

| Fixture | Inputs | Required observation |
|---|---|---|
| Overlap | A says “Use local backup.” B says “Use local backup.” | Report shared position with both exact sources. |
| Opposed | A says “Enable remote access.” B says “Do not enable remote access.” | Report incompatible recommendations on remote access with both references; no shared endorsement. |
| Minority and identity | Two aliases of one confirmed family prefer A. A distinct family favors B. One unconfirmed pasted source also favors A. | Preserve B and manual source; independently confirmed families favoring A count at most once. |
| Paraphrase and ambiguity | A says “Keep the database local.” B says “Store records on this machine.” Compare also B′ “The machine may be remote.” | A/B give supported overlap or explicit semantic limitation. B′ cannot support a positive agreement without context. Preserve both original positions. |
| Citation and unknown support | A cites a URL supplied only by a model. B makes an unsupported claim; C times out. | Label A's citation as unverified provider-supplied support, B's support missing, C missing. No fetch, fabricated citation or independent verification. |
| One source and corruption | Only A succeeds; repeat with foreign/missing response ID or a span that changes the cited negation. | Single-source report records limitation with no inter-model agreement. Reject malformed evidence, publish nothing and retain A. |


For delayed dispatch, verify the sent bytes derive solely from the admission projection with any subsequent policy restrictions. Run all six [comparison examples](comparison-fixtures.md) for P0-12.
